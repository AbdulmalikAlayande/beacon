# 0009. Entities hold data only, with string enums, ID-only equality and IDs created in code

- Status: Accepted
- Date: 2026-11-02
- Register entries: D-035, D-036, D-037, D-038
- Document status: Approved, last checked against the code on 2026-11-02

## Context

Beacon's JPA entities are where several earlier problems showed up:

- Lifecycle callbacks set timestamps without the `Clock` and silently overwrote test data.
- `String` IDs did not match the `UUID` columns and broke `ddl-auto=validate`.
- A task needs its identity before it enters any queue, including a broker that has no database to generate one.

## Decision

- Every `@Enumerated` field uses `EnumType.STRING`, never `ORDINAL`.
- `equals` and `hashCode` compare the `id` and nothing else. Tests check stored data with field-by-field assertions, never with `equals`.
- Entities hold data only. There are no `@PrePersist` or `@PreUpdate` callbacks. Whoever creates or changes a row sets its times from the injected `Clock`.
- IDs are `UUID` everywhere: in the DTO, the entities, the event and the columns.
- The task ID is created with `UUID.randomUUID()` when the `DeliveryTask` is built, in the listener. `DeliveryTaskEntity` stores it with a plain `@Id`, without `@GeneratedValue`.

## Consequences

- Reordering an enum cannot corrupt stored data.
- Because `equals` uses only the ID, an equality check in a test proves nothing about the other fields.
- Timestamps are testable, because they all come from the `Clock` (ADR 0006).
- A task has the same ID in every queue implementation.
- An entity with an ID that is set in code looks "not new" to Spring Data unless it implements `Persistable`. Today `DeliveryTaskEntity` does not, so `save()` runs a select before each insert (register G-20).

## Alternatives rejected

- **`@PrePersist` and `@PreUpdate` setting timestamps.** Rejected because callbacks cannot reach the `Clock` bean, and they overwrote test data.
- **`@GeneratedValue` on the queue entity ID, or database-generated task IDs.** Rejected because the task needs its ID before any queue sees it.
- **`String` IDs on the entities and DTO.** Rejected because they did not match the `UUID` columns and broke `ddl-auto=validate`.
- **`EnumType.ORDINAL`.** Rejected because reordering or inserting an enum constant would silently change the meaning of every stored row. Strings stay correct and are readable in SQL.

## In the code

- `beacon-core/src/main/java/io/github/abdulmalikalayande/beacon/core/entity/DeliveryTaskEntity.java` (plain `@Id`, string enums, ID-only `equals`)
- `beacon-core/src/main/java/io/github/abdulmalikalayande/beacon/core/entity/NotificationStatusEntity.java` (string enums, `fromTask(DeliveryTask, Clock)`)
- `beacon-core/src/main/java/io/github/abdulmalikalayande/beacon/core/listener/NotificationRequestedEventListener.java` (`UUID.randomUUID()` in `createDeliveryTask`)
- `beacon-api/src/main/java/io/github/abdulmalikalayande/beacon/api/dto/DeliveryTask.java` (`UUID taskId`, `UUID notificationId`)
- Not yet true:
  - `NotificationStatusEntity` still lets Hibernate generate its ID (`@GeneratedValue(strategy = GenerationType.UUID)`), and its `equals` throws a `NullPointerException` while the ID is still null (register G-09).
  - `deduplication_store.id` is generated by the database (G-29).
  - `notificationId` is a `String`, not a `UUID`, in several `beacon-api` types (G-25).
